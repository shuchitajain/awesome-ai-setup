# Architecture

This document describes the structure, layers, and conventions of this Node.js REST API. It is the primary context file for AI tools to understand where code belongs and how the system is organized.

---

## System Overview

This API uses a **layered architecture** with four layers: routes, controllers, services, and repositories. Business logic lives exclusively in services. Data access lives exclusively in repositories. Controllers are thin - they validate input, call a service, and return a response.

The dependency direction is strictly one-way: routes → controllers → services → repositories → database. No layer imports from a layer above it.

**Stack:** Express 5 + TypeScript (strict mode) + Prisma + Zod + Vitest + Pino

## Layer Conventions

### Routes (`src/routes/`)
- Register middleware and delegate to controllers
- No business logic, no direct database access
- Authentication applied at route level via `authMiddleware`
- Validation applied at route level via `validate(Schema)` factory

```typescript
// routes/products.ts
router.post('/', authMiddleware, validate(CreateProductSchema), ProductController.create);
router.get('/:id', ProductController.getById);
```

### Controllers (`src/controllers/`)
- Extract validated request data, call one service method, return response
- Never call repositories directly - always go through services
- Never contain `if/else` business logic
- Error propagation: throw errors and let the error middleware handle them

```typescript
// controllers/ProductController.ts
static async create(req: Request, res: Response) {
  const product = await productService.create(req.body, req.user.id);
  res.status(201).json({ data: product });
}
```

### Services (`src/services/`)
- All business logic lives here - this is where conditions, validation rules, and workflows go
- No Express imports - no `Request`, `Response`, or `NextFunction`
- No direct Prisma calls - use repositories
- Call other services when needed (cross-domain operations)
- Throw typed `ApiError` subclasses on failure

```typescript
// services/ProductService.ts
async create(data: CreateProductInput, ownerId: string) {
  const existing = await this.productRepo.findBySkuAndOwner(data.sku, ownerId);
  if (existing) throw new ConflictError('product', 'sku', data.sku);
  return this.productRepo.create({ ...data, ownerId });
}
```

### Repositories (`src/repositories/`)
- All Prisma queries live here - no Prisma calls outside repositories
- Return domain objects, not raw Prisma results
- Handle `PrismaClientKnownRequestError` and translate to domain errors where appropriate
- One repository per Prisma model

## Error Handling

All errors extend `ApiError` from `src/utils/errors.ts`. The `errorHandler` middleware in `src/middleware/errorHandler.ts` is the single place where errors are serialized to HTTP responses.

```
ApiError (base)
├── ValidationError     → 400
├── UnauthorizedError   → 401
├── ForbiddenError      → 403
├── NotFoundError       → 404
├── ConflictError       → 409
└── InternalError       → 500
```

Never return raw error messages or stack traces in production responses. The error handler checks `NODE_ENV` before including `details`.

---

## Response Format

All responses follow a consistent envelope:

**Success:**
```json
{ "data": { ... } }
```

**Paginated success:**
```json
{ "data": [...], "meta": { "page": 1, "limit": 20, "total": 150 } }
```

**Error:**
```json
{ "error": { "code": "PRODUCT_NOT_FOUND", "message": "Product not found: abc123" } }
```

Never return raw arrays at the top level. Always wrap in `{ "data": [...] }`.

## Authentication

JWT access tokens (15-minute expiry) + refresh tokens (7-day expiry, stored in database).

- Access token: sent in `Authorization: Bearer <token>` header
- Refresh token: sent in `POST /auth/refresh` request body
- Token signing: `src/utils/jwt.ts` - uses `jsonwebtoken` with env-validated secret
- `authMiddleware` attaches the decoded user to `req.user` (typed via `src/types/express.d.ts`)
- Refresh tokens are stored in the `RefreshToken` Prisma model and invalidated on use (rotation)

---

## Environment Config

All environment variables are validated at startup in `src/env.ts` via a Zod schema. The app refuses to start if required variables are missing or malformed.

Import `env` from `src/env.ts` everywhere - never access `process.env` directly outside that file.

---

## Database

Prisma with PostgreSQL. Schema lives in `prisma/schema.prisma`.

- Migrations: `npx prisma migrate dev` (development), `npx prisma migrate deploy` (production)
- Client: singleton exported from `src/db.ts` - import `db` everywhere, never `new PrismaClient()`
- Transactions: use `db.$transaction()` for any operation touching multiple models
- Never call Prisma outside `src/repositories/`

---

## Testing

- **Unit tests** (`tests/unit/`): test services and utilities in isolation. Mock repositories with `vi.fn()`. No database, no HTTP.
- **Integration tests** (`tests/integration/`): spin up real Express app + real test database. Use `tests/fixtures/db.ts` to clean up between tests.
- Test files mirror `src/` structure: `src/services/UserService.ts` → `tests/unit/services/UserService.test.ts`
- Use `tests/fixtures/factories.ts` for test data - never hardcode raw objects in test files
